# What is a Span Processor?

A Span Processor decides what happens when a span finishes.

When a request completes:

GET /

↓

Span Created

↓

Endpoint Executes

↓

Span Ends

↓

Span Processor receives it

The processor can:
    Export it to Azure
    Export it to Jaeger
    Export it to Datadog
    Write it to a file
    Drop it

The processor makes that decision.

# Why not export immediately?

Imagine your API handles:

1000 requests/second

If every request immediately performed:

HTTPS

↓

Azure

your response time would become much slower.

Instead:

    Request
    ↓
    Finish Span
    ↓
    Put into Queue
    ↓
    Background Thread
    ↓
    Azure

The user gets their response quickly, while exporting happens in the background.

This is why BatchSpanProcessor exists.

# Types of Span Processors

There are two common processors.

1. SimpleSpanProcessor

↓

Good for:

Learning
Small examples

2. BatchSpanProcessor ⭐
Request 1

↓

Queue

Request 2

↓

Queue

Request 3

↓

Queue

───────────────

Every few seconds

↓

Send one batch

↓

Azure

This is what nearly all production applications use.

# Update telemetry.py

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

provider = TracerProvider()

processor = BatchSpanProcessor(
    span_exporter=None
)

provider.add_span_processor(processor)

trace.set_tracer_provider(provider)

# Why separate the Provider and Processor?

This is a common software design pattern: separation of concerns.
The TracerProvider is responsible for creating and managing spans.
The BatchSpanProcessor is responsible for handling completed spans.

# This separation means you can:

Change where telemetry goes without changing how spans are created.
Add multiple processors (for example, one sending to Azure and another writing to the console).
Swap processors depending on the environment.
